# Jana Address: как это работает и как проверить своими глазами

Этот документ — короткая экскурсия по готовому локальному решению. Здесь нет
официальных адресов из закрытых файлов: примеры ниже полностью синтетические.

## 1. Что это за программа

Jana Address принимает строку адреса и раскладывает её на отдельные поля:
область, город, район, жилой массив, тип и название улицы, дом, квартиру,
подъезд, этаж и ориентир.

Программа работает локально на Mac:

- браузер открывает интерфейс на `http://127.0.0.1:8080`;
- локальный Python-сервис принимает JSON;
- локальная SQLite-база `data/public/gazetteer.sqlite` помогает узнавать
  географические названия;
- адреса не отправляются во внешний геокодер или облачный API;
- Docker ограничен 768 MiB памяти, read-only filesystem и localhost-портом.

Простой путь данных:

```text
JSON-файл или браузер
        ↓
FastAPI: размер и формат запроса
        ↓
validate_batch: id + raw_address, UTF-8, лимиты
        ↓
parse_batch: разбор текста и поиск в локальном справочнике
        ↓
validate_output: ровно 14 полей, тот же id/raw/order
        ↓
JSON-ответ и два варианта экспорта в интерфейсе
```

## 2. Где смотреть код в VS Code

Открывайте файлы в таком порядке:

1. `compose.yaml` — как запускается и ограничивается контейнер.
2. `Dockerfile` — что именно помещается внутрь образа.
3. `backend/jana/api.py` — приём HTTP-запроса и возврат ответа.
4. `backend/jana/contracts.py` — правила входного и выходного JSON.

6. `backend/jana/gazetteer.py` — работа с локальным SQLite-справочником.
7. `backend/jana/streaming.py` — ограниченная по памяти обработка больших

8. `tests/test_api.py` — автоматические проверки API и offline-защиты.
9. `docs/research/FINAL_DOCKER_ACCEPTANCE_2026-10-18.md` — результаты
   финальной проверки готового образа.

## 3. Как читается входящий JSON

### Обычный HTTP-запрос

HTTP API ожидает **массив** объектов. У каждого объекта обязательны две строки:

```json
[
  {
    "id": "demo-1",
    "raw_address": "Астана, ул. Сынақ, дом 12/3, кв. 7"
  },
  {
    "id": "demo-1",
    "raw_address": "Алматы, Abai daңғyly 25, 2 кіреберіс"
  }
]
```

Повторяющийся `id` допустим. Каждая строка остаётся отдельной записью и
остаётся на том же месте в ответе.

В `backend/jana/api.py` происходит следующее:

1. `BodyLimitMiddleware` считает реально полученные байты и не позволяет
   загрузить больше 10 MiB.
2. `read_records()` принимает либо `application/json`, либо один файл из
   `multipart/form-data`.
3. `json.loads()` разбирает UTF-8 JSON. `NaN`, `Infinity`, повреждённый JSON и
   слишком глубокая структура отклоняются.
4. `validate_batch()` из `contracts.py` проверяет весь пакет.
5. Если хотя бы одна запись неправильная, весь пакет отклоняется. Частичный
   «как будто успешный» ответ не возвращается.

Основные входные ограничения:

| Что проверяется | Правило |
|---|---|
| Верхний уровень | JSON-массив |
| Запись | JSON-объект |
| `id` | строка, не более 1024 символов |
| `raw_address` | строка, не более 8192 символов |
| Число записей | не более 10 000 в одном HTTP-пакете |
| Размер HTTP body | не более 10 MiB |
| Кодировка | корректный UTF-8 |

Лишние входные ключи не попадают в результат. Сервис оставляет только `id` и
`raw_address`, поэтому случайное поле клиента не может изменить контракт.

### Большой локальный файл

Для 50 000–500 000 строк используется не один огромный HTTP-массив, а NDJSON:
один JSON-объект на каждой физической строке.

```text
{"id":"1","raw_address":"Астана, ул. Сынақ, 1"}
{"id":"1","raw_address":"Алматы, Abai 25"}
{"id":"3","raw_address":"неполный адрес"}
```

`backend/jana/streaming.py` читает файл построчно и формирует порции по 250
записей. Следующая порция не читается, пока не обработана предыдущая. Результат
сначала пишется во временный файл, а затем публикуется атомарно: при ошибке
старый готовый результат не заменяется обрезанным файлом.

## 4. Как разбирается адрес

После входной проверки `parse_batch()` обрабатывает записи по порядку:

1. Нормализует текст для поиска, сохраняя исходный `raw_address` без изменений.
2. Распознаёт явные маркеры: область, город, район, улица, дом, квартира,
   подъезд, этаж, ЖК/жилой массив и ориентир.
3. Учитывает русскую, казахскую, латинскую и смешанную запись, сокращения и
   часть распространённых опечаток.
4. Сопоставляет найденные названия с локальным справочником КАТО/OSM.
5. Проверяет родительский контекст: например, улица не должна молча
   подставляться из другого города только из-за совпавшего названия.
6. Если город или область уже подтверждены, а для указанного номера дома в
   справочнике есть ровно одна подходящая адресная точка, может дополнить
   пропущенные город, район и область. Например, сочетание «Алматинская
   область + улица Главная + дом 7» даст район только тогда, когда внутри этой
   области такая привязка однозначна.
7. Если одноимённые улицы или такой же дом встречаются в нескольких местах,
   либо область противоречит справочнику, ничего не угадывает: неподтверждённые
   поля остаются `null`, а запись помечается как неоднозначная.
8. Вычисляет `confidence` от 0 до 1. Это рабочая эвристика для очереди
   проверки оператором, а не математическая вероятность безошибочности.

Приоритет проверки выглядит так:

```text
явно написанное в адресе
        ↓
подтверждённый город или область
        ↓
тип и название улицы
        ↓
точное совпадение номера дома в локальном справочнике
        ↓
однозначные родительские поля: город / район / область
```

Номер дома без города или области не считается достаточным доказательством:
одинаковые улицы и дома существуют в разных населённых пунктах.

Проверить новую возможность на текущем публичном справочнике можно так:

```bash
curl -sS -X POST http://127.0.0.1:8080/parse \
  -H 'Content-Type: application/json' \
  --data '[{"id":"demo-district","raw_address":"Алматы, проспект Рыскулова, дом 30"}]' \
  | python3 -m json.tool
```

В результате район заполняется как `Жетысуский`. Если заменить номер дома на
отсутствующий в справочнике, район останется `null`: это наглядно показывает,
что программа использует точную адресную точку, а не случайный район улицы.

Справочник — обычный локальный SQLite-файл. Интернет для разбора не нужен.

## 5. Как проверяется выход

Перед отправкой клиенту `validate_output()` проверяет каждую запись:

- количество результатов равно количеству входов;
- порядок записей не изменён;
- `id` и `raw_address` совпадают с соответствующим входом;
- повторяющиеся ID не исчезли и не объединились;
- присутствуют ровно 14 полей и в фиксированном порядке;
- текстовые поля содержат строку или `null`;
- `confidence` — конечное число от 0 до 1.

Порядок 14 полей:

```text
id, raw_address, province, city, district, living_area,
street_type, street_name, house, apartment, entrance, floor,
landmark, confidence
```

Если парсер вернёт неправильную структуру, API отдаст безопасную ошибку
`PARSER_FAILURE`, а не частичный результат и не внутренний traceback.

## 6. Запуск на этом Mac

Откройте терминал VS Code: меню **Terminal → New Terminal**. Затем выполните:

```bash
cd /Users/phonelab/Documents/HACKATHON

```

В колонке состояния должно быть `healthy`. Проверка readiness:


```bash

```

Сейчас финальный образ уже собран локально. Флаг `--no-build` важен: он
показывает, что запускается готовый образ без скачивания и пересборки.

## 7. Проверка своим JSON-файлом

Создайте в VS Code файл `data/private/my_test.json` с синтетическим содержимым
из раздела 3. Затем отправьте его в API и сохраните ответ:

```bash
curl -sS -X POST http://127.0.0.1:8080/parse \
  -H 'Content-Type: application/json' \
  --data-binary @data/private/my_test.json \
  -o output/my_result.json

python3 -m json.tool output/my_result.json
```

Проверка того же файла как загрузки формы:

```bash
curl -sS -X POST http://127.0.0.1:8080/parse \
  -F 'file=@data/private/my_test.json' \
  -o output/my_result_multipart.json

cmp output/my_result.json output/my_result_multipart.json
```

Если `cmp` ничего не напечатал и завершился успешно, оба способа загрузки дали
одинаковый ответ.

Можно специально отправить неправильный верхний уровень:

```bash
curl -sS -X POST http://127.0.0.1:8080/parse \
  -H 'Content-Type: application/json' \
  --data '{"id":"x","raw_address":"test"}' | python3 -m json.tool
```

Ожидаемый ответ содержит код `EXPECTED_ARRAY`.

## 8. Проверка через интерфейс

1. Откройте `http://127.0.0.1:8080`.
2. Убедитесь, что интерфейс показывает подключённый сервер и режим API.
3. Нажмите **Демо-пакет** или загрузите `data/private/my_test.json`.
4. Откройте запись и сравните исходную строку с выделенными полями.
5. Переключите фильтр **На проверку** — там строки с низкой уверенностью или
   обязательными пропусками.
6. Измените одно поле и сохраните. `raw_address` при этом не меняется.
7. Скачайте **Результат API** и **С правками**. Первый файл остаётся исходным
   ответом движка, второй включает только операторские исправления.

## 9. Автоматические тесты

Полный тестовый набор можно повторить в изолированном тестовом контейнере:

```bash
docker run --rm --network none --read-only \
  --tmpfs /tmp:size=128m,mode=1777 \
  --cap-drop ALL --security-opt no-new-privileges:true \
  -v "$PWD:/src:ro" -w /src \
  -e PYTHONPATH=/src/backend:/src \
  jana-address:fulltest python -m pytest -q
```

Подтверждённый результат финального прогона:

```text
680 passed, 255 subtests passed
```

Проверка холодного запуска и HTTP-пакета из 1000 строк требует сначала
остановить текущий контейнер, затем verifier сам снова его поднимет:

```bash
docker compose down
python3 tools/verify_container.py \
  --input output/corpus/test-1000/input.json \
  --report output/my-container-verification.json
```

После команды сервис снова остаётся запущенным. Отчёт содержит время от
`docker compose up` до readiness и реальный HTTP benchmark.

## 10. Проверка потокового режима

Создайте в `data/private/my_test.ndjson` по одному объекту на строку, как в
разделе 3. Затем:

```bash
mkdir -p output/manual
docker run --rm --network none --memory 768m --memory-swap 768m \
  --read-only --tmpfs /tmp:size=32m,mode=1777 \
  --cap-drop ALL --security-opt no-new-privileges:true \
  --user "$(id -u):$(id -g)" \
  -v "$PWD/data/private:/input:ro" \
  -v "$PWD/output/manual:/output:rw" \
  jana-address:local \
  python /app/tools/parse_stream.py \
  --input /input/my_test.ndjson \
  --output /output/my_test_result.json \
  --gazetteer /app/data/public/gazetteer.sqlite \
  --batch-size 250
```

Прогресс выводится без адресов и ID. Готовый обычный JSON-массив появится в
`output/manual/my_test_result.json` только после полного успешного прохода.
